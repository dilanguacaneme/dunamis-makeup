## 2. Modelo de Datos y Contratos de Comunicación

### 2.1. Entidades de Persistencia JPA

#### Entidad `Factura.java` (Tabla `factura`)
- `id`: `Long` (`BIGINT GENERATED BY DEFAULT AS IDENTITY`, PK).
- `cliente`: `String` (`VARCHAR(255)`, no nulo, trim, max 255).
- `telefonoCliente`: `String` (`VARCHAR(30)`, nullable, trim, max 30).
- `vendedorNombre`: `String` (`VARCHAR(120)`, no nulo).
- `vendedorUsuario`: `String` (`VARCHAR(50)`, no nulo, indexado para segregación RBAC).
- `fecha`: `LocalDateTime` (`TIMESTAMP WITHOUT TIME ZONE`, no nulo) — *Migrado de `LocalDate` para trazabilidad horaria (RF-020)*.
- `total`: `Double` (`DOUBLE PRECISION`, no nulo, `>= 0.0`).
- `estadoPago`: `EstadoPagoFactura` (`VARCHAR(30)`, no nulo, enum: `PAGADA`, `ABONO_PARCIAL`, `PENDIENTE`).
- `valorAbonado`: `Double` (`DOUBLE PRECISION`, no nulo, por defecto `0.0`).
- `saldoPendiente`: `Double` (`DOUBLE PRECISION`, no nulo, calculado como `total - valorAbonado`).
- `anulada`: `Boolean` (`BOOLEAN NOT NULL DEFAULT FALSE`).
- `fechaAnulacion`: `LocalDateTime` (`TIMESTAMP WITHOUT TIME ZONE`, nullable).
- `motivoAnulacion`: `String` (`VARCHAR(500)`, nullable).
- `detalles`: `List<DetalleFactura>` (`@OneToMany(mappedBy = "factura", cascade = CascadeType.ALL, orphanRemoval = true)`).
- `abonos`: `List<AbonoFactura>` (`@OneToMany(mappedBy = "factura", cascade = CascadeType.ALL, orphanRemoval = true)`).

#### Entidad `DetalleFactura.java` (Tabla `detalle_factura`)
- `id`: `Long` (`BIGINT GENERATED BY DEFAULT AS IDENTITY`, PK).
- `factura`: `Factura` (`@ManyToOne`, foreign key `factura_id`, no nulo).
- `producto`: `Producto` (`@ManyToOne`, foreign key `producto_id`, no nulo).
- `cantidad`: `Integer` (`INTEGER`, no nulo, `> 0`).
- `precioUnitario`: `Double` (`DOUBLE PRECISION`, no nulo, snapshot del precio del producto al momento de venta).
- `subtotal`: `Double` (`DOUBLE PRECISION`, no nulo, calculado como `precioUnitario * cantidad`).

#### Entidad `AbonoFactura.java` (Tabla `abono_factura`)
- `id`: `Long` (`BIGINT GENERATED BY DEFAULT AS IDENTITY`, PK).
- `factura`: `Factura` (`@ManyToOne`, foreign key `factura_id`, no nulo).
- `monto`: `Double` (`DOUBLE PRECISION`, no nulo, `> 0.0`).
- `fecha`: `LocalDateTime` (`TIMESTAMP WITHOUT TIME ZONE`, no nulo, por defecto `LocalDateTime.now()`).
- `medioPago`: `MedioPago` (`VARCHAR(30)`, no nulo, enum: `EFECTIVO`, `TRANSFERENCIA`, `NEQUI`, `DAVIPLATA`, `TARJETA`, `OTRO`).
- `notas`: `String` (`VARCHAR(255)`, nullable, referencia o nota de auditoría).
- `usuarioRegistro`: `String` (`VARCHAR(50)`, no nulo, username del operador).

---

### 2.2. Enumeradores Tipados

1. **`EstadoPagoFactura`:**
   - `PAGADA`: Deuda saldada en su totalidad (`saldoPendiente == 0.0`).
   - `ABONO_PARCIAL`: Registra al menos un abono pero mantiene saldo positivo adeudado (`saldoPendiente > 0.0`).
   - `PENDIENTE`: Venta a crédito o por cobrar sin abono inicial (`valorAbonado == 0.0`).

2. **`MedioPago`:**
   - `EFECTIVO`, `TRANSFERENCIA`, `NEQUI`, `DAVIPLATA`, `TARJETA`, `OTRO`.

    List<CrearDetalleFacturaRequest> detalles,

    Long productoId,

    @NotNull(message = "La cantidad es obligatoria")
    @Min(value = 1, message = "La cantidad debe ser mayor que cero")
    Integer cantidad
) {}

public record FacturaResponse(

    String cliente,
    String telefonoCliente,
    String vendedorNombre,

## 3. Decisiones Técnicas Justificadas y Alternativas Descartadas

### Decisión 1: Erradicación Absoluta de Entidades JPA en Controladores y Adopción de DTOs Inmutables
- **Decisión:** Sustituir la exposición y binding directo de las entidades `Factura` y `DetalleFactura` por los records inmutables `CrearFacturaRequest`, `FacturaResponse`, `DetalleFacturaResponse`, `RegistrarAbonoRequest` y `AbonoResponse`.
- **Justificación:** Cumple taxativamente con el **Principio 2 de la Constitución** ("Comunicación exclusiva con DTOs validados; no exponer entidades JPA directamente"). Elimina el riesgo de *over-posting* / *mass-assignment* (donde un usuario malintencionado podría inyectar precios, alterar el `total` o manipular el `id`).
- **Alternativa Descartada:** Mantener las entidades JPA con anotaciones `@JsonView` o `@JsonIgnore`. *Descartada por violar la Constitución, acoplar la capa de transporte al esquema relacional de PostgreSQL y dificultar el versionado del API.*
- **Requisitos cubiertos:** **RF-001, RF-002, RF-003, RF-014**.

---

### Decisión 2: Atomicidad Transaccional `@Transactional` con Validación Preventiva y Rollback Total
- **Decisión:** La creación de facturas (`crearFactura`) y la anulación (`anularFactura`) operan bajo `@Transactional` de Spring. Antes de persistir cualquier cambio, se consolidan cantidades repetidas, se verifica la existencia y estado activo de los productos y se comprueba que el inventario sea suficiente. Si falla un solo ítem, se arroja una excepción de negocio que dispara un rollback total.
- **Justificación:** Satisface el **Principio 4 de la Constitución** ("Integridad transaccional: Facturación y stock son atómicos; nunca permitir stock negativo"). Garantiza que la base de datos nunca quede en estado inconsistente (facturas huérfanas o deducciones parciales de stock).
- **Alternativa Descartada:** Descontar existencias producto por producto de manera secuencial sin transacción y capturar errores de forma aislada. *Descartada porque si el 5to producto falla por falta de stock, los 4 anteriores quedarían descontados sin haberse emitido la venta.*
- **Requisitos cubiertos:** **RF-003, RF-004, RF-005, RF-006, RF-017**.

---

### Decisión 3: Snapshot de Precio Unitario en `DetalleFactura`
- **Decisión:** Registrar el campo `precioUnitario` en cada `DetalleFactura` tomado directamente del precio vigente del producto en el momento de la venta.
- **Justificación:** Garantiza la inmutabilidad histórica contable. Si un producto sube o baja de precio el próximo mes, las facturas emitidas en el pasado conservan el precio exacto al que se concretó la venta.
- **Alternativa Descartada:** Calcular los subtotales en tiempo real haciendo `detalle.getProducto().getPrecio() * detalle.getCantidad()`. *Descartada porque un cambio en el catálogo de cosméticos desvirtuaría retrospectivamente los montos de facturas ya emitidas.*
- **Requisitos cubiertos:** **RF-001, RF-003**.

---

### Decisión 4: Modelo Financiero de Abonos Parciales con Validación Estricta de No Sobrepago
- **Decisión:** Implementar la entidad dedicada `AbonoFactura` vinculada a `Factura`. Cada abono valida que `monto > 0` y `monto <= saldoPendiente`. La factura recalcula `valorAbonado = valorAbonado + monto`, actualiza `saldoPendiente` y, si este llega a 0, transiciona automáticamente a `PAGADA`.
- **Justificación:** Resuelve el vacío funcional identificado en `checklist-sdd.md`. Dota al negocio de soporte formal para ventas a crédito y pagos por cuotas (muy común en comercio de cosméticos), protegiendo la caja de sobrepagos accidentales.
- **Alternativa Descartada:** Solo actualizar un campo numérico `valorAbonado` en la tabla `factura` sin crear tabla de abonos. *Descartada porque elimina la auditoría de pagos (no se sabría quién recibió el dinero, qué fecha/hora se abonó ni por qué medio: Nequi, efectivo o tarjeta).*
- **Requisitos cubiertos:** **RF-002, RF-014, RF-015, RF-016**.

---

### Decisión 5: Flujo de Anulación con Restitución Automática de Stock Exclusivo para Administradoras
- **Decisión:** Exponer `POST /factura/{id}/anular`, restringido con `@PreAuthorize("hasRole('ADMIN')")`. La operación valida que la factura no esté ya anulada (`409 Conflict`), incrementa el stock de cada producto en la cantidad facturada, recalcula `totalProducto`, marca la factura como anulada (`anulada = true`) y guarda fecha y motivo.
- **Justificación:** Proporciona un mecanismo seguro y reversible para cancelar ventas emitidas por error humano o devoluciones de clientes, asegurando que el inventario físico coincida con el sistema contable sin permitir cancelaciones no autorizadas por dependientes de mostrador.
- **Alternativa Descartada:** Eliminar físicamente el registro de la factura con `DELETE`. *Descartada por violar normativas de auditoría fiscal, impedir el seguimiento de comprobantes cancelados y destruir la integridad referencial.*
- **Requisitos cubiertos:** **RF-017, RF-018, RF-019**.

---

### Decisión 6: Migración de `fecha` a `LocalDateTime` con Compatibilidad Brownfield
- **Decisión:** Migrar el tipo de dato de `Factura.fecha` de `LocalDate` a `LocalDateTime`. Para registros preexistentes en la base de datos PostgreSQL, la capa de persistencia interpreta fechas sin hora asignando `00:00:00`. Facturas históricas sin estado de pago se asumen como `PAGADA` con `saldoPendiente = 0.0`.
- **Justificación:** Cumple con el **Principio 12 de la Constitución** (Compatibilidad Brownfield). Permite auditorías cronológicas intra-día (identificar ventas de la mañana vs de la tarde) sin romper los datos existentes.
- **Alternativa Descartada:** Mantener `LocalDate` y agregar una columna secundaria `hora: LocalTime`. *Descartada por redundancia estructural y dificultad en ordenamientos JPQL `ORDER BY fecha DESC`.*
- **Requisitos cubiertos:** **RF-020**.

---

### Decisión 7: Segregación RBAC de Facturas por Vendedor
- **Decisión:** `GET /factura/obtener-facturas` y `GET /factura/obtener-factura-por-id/{id}` retornan todas las ventas si el usuario es `ADMIN`, o únicamente las asociadas a su propio `vendedorUsuario` si es `VENDEDOR`. Si un vendedor intenta consultar una factura ajena por ID, recibe HTTP `403 Forbidden` (o `404 Not Found`).
- **Justificación:** Garantiza la confidencialidad entre vendedores y previene vulnerabilidades IDOR (Insecure Direct Object Reference).
- **Alternativa Descartada:** Permitir que todos los usuarios vean todas las facturas y solo filtrar en el frontend mediante JavaScript. *Descartada por ser una pésima práctica de seguridad que expone información sensible en la red.*
- **Requisitos cubiertos:** **RF-008, RF-009, RF-011, RF-013**.

### 4.1. Pruebas Backend (`src/test/java/com/dunamis/makeup/`)

1. **`FacturaDtoTest` (Validación de Bean Validation y Contratos):**
   - Validar que `CrearFacturaRequest` rechace cliente en blanco o nulo, lista de detalles vacía o nula, o detalles con productoId nulo o cantidad `<= 0`.
   - Validar que `RegistrarAbonoRequest` rechace monto `<= 0` o nulo, y medio de pago nulo.
   - Validar inmutabilidad y serialización JSON de `FacturaResponse` y `AbonoResponse`.

2. **`FacturaServiceTest` (Pruebas Unitarias de Lógica y Transacciones con Mockito):**
   - Creación exitosa: cálculo exacto de subtotales y total, descuento unitario de existencias, recálculo de `totalProducto` y asignación de vendedor.
   - Estado de pago inicial: `PAGADA` (abono total), `PENDIENTE` (abono 0), `ABONO_PARCIAL` (abono entre 0 y total).
   - Rechazo de venta con producto inexistente (`ProductoNoEncontradoException` / 404).
   - Rechazo de venta con producto inactivo (`activo = false` / 400).
   - Rechazo de venta por stock insuficiente (`ProductoInsuficienteException` / 409).
   - Consolidación de ítems: si el request envía 2 veces el mismo `productoId`, se suman sus cantidades para validar stock una sola vez.
   - Registro de abono exitoso con transición automática a `PAGADA` cuando `saldoPendiente == 0`.
   - Rechazo de abono si excede el saldo pendiente (validación de no sobrepago).
   - Rechazo de abono sobre factura anulada o factura ya pagada.
   - Anulación de factura por `ADMIN`: restitución exacta del stock a los productos y marcado `anulada = true`.
   - Rechazo de re-anulación si la factura ya estaba anulada (`409 Conflict`).

3. **`FacturaIntegrationTest` (MockMvc + Base de Datos en Memoria):**
   - `POST /factura/crear`: 201 Created con cookie de sesión y CSRF; verificación de factura persistida y stock decrementado en base de datos.
   - `GET /factura/obtener-facturas`: 200 OK con lista ordenada cronológicamente; verificación de segregación de registros para vendedor.
   - `GET /factura/obtener-factura-por-id/{id}`: 200 OK con DTO completo y 404 estructurado `{ "error": "NOT_FOUND" }` ante ID inexistente.
   - `POST /factura/{id}/abonos`: 201 Created con actualización del saldo de la factura.
   - `GET /factura/{id}/abonos`: 200 OK con historial de abonos.
   - `POST /factura/{id}/anular`: 200 OK como `ADMIN` verificando la reposición de existencias en catálogo.

4. **`FacturaRbacSecurityTest` (Seguridad y Control de Acceso):**
   - `POST /factura/crear` sin autenticación -> 401 Unauthorized estructurado.
   - `GET /factura/obtener-facturas` como `VENDEDOR` -> solo lista sus propias facturas.
   - `GET /factura/obtener-factura-por-id/{id}` como `VENDEDOR` intentando ver factura de otro -> 403 Forbidden.
   - `POST /factura/{id}/anular` como `VENDEDOR` -> 403 Forbidden interceptado por Spring Security.
   - `POST /factura/{id}/anular` como `ADMIN` -> 200 OK permitido.
