## 2. Modelo de Datos y Contratos de Comunicación

### 2.1. Entidad de Persistencia JPA (`Producto.java`)
Tabla PostgreSQL `producto`:
- `id`: `Long` (`BIGINT GENERATED BY DEFAULT AS IDENTITY`, PK).
- `nombre`: `String` (`VARCHAR(255)`, no nulo).
- `precio`: `Double` (`DOUBLE PRECISION`, no nulo, `>= 0.0`).
- `cantidad`: `Integer` (`INTEGER`, no nulo, `>= 0`).
- `cantidadInicial`: `Integer` (`INTEGER`, nullable, snapshot inicial).
- `totalProducto`: `Double` (`DOUBLE PRECISION`, nullable, calculado como `precio * cantidad`).
- `categoria`: `CategoriaProducto` (`VARCHAR(32)`, no nulo, `EnumType.STRING`).
- `marca`: `Marca` (`@ManyToOne`, foreign key `marca_id`, nullable para compatibilidad previa).
- `activo`: `Boolean` (`BOOLEAN NOT NULL DEFAULT TRUE`) — **Nuevo campo de control para borrado lógico**.

> [!NOTE]
> Para garantizar compatibilidad retrospectiva (Principio 12) con registros existentes en bases de datos brownfield donde `activo` sea nulo, se implementa `@PrePersist` / `@PostLoad` o inicialización por defecto `Boolean.TRUE` garantizando que ningún registro histórico se interprete accidentalmente como inactivo.

### 2.2. Contratos DTO Tipados (Principio 2 de la Constitución)

1. **`ProductoResponse` (Salida tipada inmutable):**
   ```java
   public record ProductoResponse(
       Long id,
       String nombre,
       Double precio,
       Integer cantidad,
       Integer cantidadInicial,
       Double totalProducto,
       CategoriaProducto categoria,
       MarcaResponse marca,
       Boolean activo
   ) {}
   ```

2. **`CrearProductoRequest` (Payload de creación `POST /producto/crear`):**
   ```java
   public record CrearProductoRequest(
       @NotBlank(message = "El nombre del producto no puede estar vacío")
       @Size(min = 2, max = 120, message = "El nombre debe tener entre 2 y 120 caracteres")
       String nombre,

       @NotNull(message = "El precio del producto no puede estar vacío")
       @DecimalMin(value = "0.0", message = "El precio no puede ser negativo")
       Double precio,

       @NotNull(message = "La cantidad no puede estar vacía")
       @Min(value = 0, message = "Las existencias no pueden ser negativas")
       Integer cantidad,

       @NotNull(message = "La categoría no puede estar vacía")
       CategoriaProducto categoria,

       @NotNull(message = "Seleccione una marca para el producto")
       Long marcaId
   ) {}
   ```

3. **`ActualizarProductoRequest` (Payload parcial `PATCH /producto/actualizar/{id}`):**
   ```java
   public record ActualizarProductoRequest(
       @Size(min = 2, max = 120, message = "El nombre debe tener entre 2 y 120 caracteres")
       String nombre,

       @DecimalMin(value = "0.0", message = "El precio no puede ser negativo")
       Double precio,

       @Min(value = 0, message = "Las existencias no pueden ser negativas")
       Integer cantidad,

       CategoriaProducto categoria,

       Long marcaId,

       Boolean activo
   ) {
       @AssertTrue(message = "Debe especificar al menos un campo válido para actualizar")
       public boolean isAnyFieldPresent() {
           return (nombre != null && !nombre.isBlank()) ||
                  precio != null ||
                  cantidad != null ||
                  categoria != null ||
                  marcaId != null ||
                  activo != null;
       }
   }
   ```

## 3. Decisiones Técnicas Justificadas y Alternativas Descartadas

### Decisión 1: Erradicación de Entidades JPA en el Controlador y Adopción Exclusiva de DTOs
- **Decisión:** Reemplazar el uso directo de la entidad `Producto` en `ProductoController` por los DTOs inmutables `ProductoResponse`, `CrearProductoRequest` y `ActualizarProductoRequest`.
- **Justificación:** Cumple de manera estricta y no negociable con el **Principio 2 de la Constitución** ("Comunicación exclusiva con DTOs validados; no exponer entidades JPA directamente"). Evita riesgos de *mass assignment* (por ejemplo, alteración arbitraria de `id` o estados internos) y desacopla los contratos HTTP del esquema de la base de datos.
- **Alternativa Descartada:** Mantener la entidad `Producto` anotada con `@JsonIgnoreProperties` o anotaciones Jackson en la entidad de persistencia. *Descartada por violar la Constitución, acoplar persistencia a transporte HTTP y dificultar el mantenimiento y versionado de la API.*
- **Requisitos cubiertos:** **RF-001, RF-002, RF-008, RF-010, RF-012, RF-014**.

---

### Decisión 2: Borrado Lógico Obligatorio ante Facturas Existentes y Salvaguarda de Integridad
- **Decisión:** En el endpoint `DELETE /producto/borrar-producto-por-id/{id}`, el sistema consulta si el producto está referenciado en `DetalleFactura` mediante `facturaRepository.existsByDetallesProductoId(id)`. Si existen facturas asociadas, se ejecuta un **borrado lógico** estableciendo `activo = false` y devolviendo `200 OK` con el DTO actualizado (o impidiendo borrado físico con `409 Conflict` si se solicita destrucción física). Si no tiene historial de ventas, se permite el borrado físico o desactivación segura.
- **Justificación:** Cumple con el **Principio 5 de la Constitución** ("Persistencia: Prohibido borrado físico de productos con facturas asociadas; usar borrado lógico"). Previene de raíz la excepción `DataIntegrityViolationException` (Error 500) y garantiza la trazabilidad contable de compras pasadas de clientes.
- **Alternativa Descartada:** Habilitar borrado en cascada (`ON DELETE CASCADE`) en PostgreSQL. *Descartada por ser destructiva y violar normativas tributarias y comerciales al desaparecer los productos vendidos de facturas históricas.*
- **Requisitos cubiertos:** **RF-015, RF-016**.

---

### Decisión 3: Consulta Diferenciada de Catálogo con RBAC Estricto (`?incluirInactivos=true`)
- **Decisión:** El endpoint `GET /producto/obtener-productos` devuelve por defecto únicamente productos activos (`activo = true`). Se admite el parámetro `?incluirInactivos=true` exclusivamente para el rol `ADMIN`. Si un `VENDEDOR` incluye este parámetro, el sistema rechaza la solicitud con HTTP `403 Forbidden` estructurado.
- **Justificación:** Mantiene total coherencia arquitectónica con el patrón establecido en la Spec 002 (Marcas). Previene que el mostrador de ventas rápidas cargue artículos descontinuados y asegura el principio de menor privilegio.
- **Alternativa Descartada:** Crear una ruta separada como `GET /producto/inactivos`. *Descartada por fragmentar el recurso REST y complicar innecesariamente el cliente web.*
- **Requisitos cubiertos:** **RF-003, RF-004, RF-005**.

---

### Decisión 4: Alerta de Stock Bajo con Umbral Configurable y Exclusión de Inactivos
- **Decisión:** Actualizar `GET /producto/acabarse` para aceptar el parámetro opcional `?umbral=<entero>` (por defecto `0`). La consulta JPQL filtra estrictamente productos con `activo = true` y `cantidad <= :umbral` ordenados por `cantidad ASC`.
- **Justificación:** Preserva compatibilidad 100% hacia atrás con el frontend actual (que asume productos agotados con `cantidad = 0`), al tiempo que faculta a administradoras y vendedoras a consultar existencias críticas (por ejemplo `?umbral=5`) para compras preventivas, descartando productos descatalogados.
- **Alternativa Descartada:** Mantener la consulta estática `WHERE p.cantidad = 0`. *Descartada porque ignora la necesidad de reabastecimiento anticipado requerida en el diagnóstico técnico de checklist-sdd.md.*
- **Requisitos cubiertos:** **RF-017, RF-018**.

---

### Decisión 5: Valuación Total de Inventario Robusta sin HTTP 404
- **Decisión:** En `GET /producto/total-inventario`, utilizar JPQL con `COALESCE(SUM(p.precio * p.cantidad), 0.0)` sobre productos activos. Si no hay productos o todos tienen existencias en 0, se retorna HTTP `200 OK` con valor `0.0`.
- **Justificación:** Corrige el antipatrón de lanzar `InventarioVacioException` con HTTP 404. Financieramente, un catálogo sin existencias vale $0.0 pesos, no un error de recurso no encontrado.
- **Alternativa Descartada:** Mantener el lanzamiento de excepción 404 e interceptarla en el frontend. *Descartada por violar la semántica HTTP y ensuciar la consola del navegador con falsos errores de red.*
- **Requisitos cubiertos:** **RF-019**.

---

### Decisión 6: Cálculo Consistente y Determinista de `totalProducto`
- **Decisión:** En toda creación, actualización o consulta, `totalProducto` se determina como `precio * cantidad`. En el DTO de salida `ProductoResponse`, se asegura la consistencia de este valor.
- **Justificación:** Elimina desincronizaciones entre el valor persistido físicamente y los valores modificados de `precio` o `cantidad`.
- **Alternativa Descartada:** Confiar en que el cliente frontend calcule el total y lo envíe en el payload. *Descartada porque abre brechas de manipulación de datos y cálculos inconsistentes.*
- **Requisitos cubiertos:** **RF-002, RF-008, RF-012**.

### 4.1. Pruebas Backend (`src/test/java/com/dunamis/makeup/`)

1. **`ProductoDtoTest` (Validación de Bean Validation):**
   - Validar que `CrearProductoRequest` rechace nombres vacíos, precios negativos, cantidades negativas, categorías nulas o marcaId nulo.
   - Validar que `ActualizarProductoRequest` rechace cuerpo sin ningún campo (`{}`) o valores inválidos.
   - Validar correcta asignación e inmutabilidad en `ProductoResponse`.

2. **`ProductoServiceTest` (Pruebas Unitarias con Mockito):**
   - Creación exitosa calculando `totalProducto`, inicializando `cantidadInicial` y `activo = true`.
   - Rechazo de creación con marca inexistente o inactiva (400 Bad Request).
   - Actualización parcial de producto recalculando `totalProducto`.
   - Rechazo de actualización con existencias o precios negativos.
   - Borrado seguro: verificar que si `facturaRepository.existsByDetallesProductoId(id)` es `true`, no se llame a `deleteById` sino que se actualice `activo = false`.
   - Valuación de inventario devolviendo 0.0 cuando el repositorio retorna `Optional.empty()`.

3. **`ProductoIntegrationTest` (MockMvc + H2 en memoria):**
   - `GET /producto/obtener-productos`: Verifica retorno de solo activos con HTTP 200 (y `[]` si vacío).
   - `GET /producto/obtener-productos?incluirInactivos=true`: Como `ADMIN` devuelve todos; como `VENDEDOR` devuelve HTTP 403 estructurado.
   - `GET /producto/obtener-productos-por-id/{id}`: Verifica 200 con DTO completo o 404 estructurado `{ "error": "NOT_FOUND" }`.
   - `POST /producto/crear`: Verifica 201 Created con CSRF y rol `ADMIN`, o 400 ante marca inactiva o validación fallida.
   - `PATCH /producto/actualizar/{id}`: Verifica 200 OK ante campos válidos, o 400 ante payload vacío.
   - `DELETE /producto/borrar-producto-por-id/{id}`: Prueba con producto con facturas (desactivación lógica 200 OK con `activo = false`) y sin facturas.
   - `GET /producto/acabarse`: Verifica comportamiento con y sin parámetro `?umbral=X`, excluyendo inactivos.
   - `GET /producto/total-inventario`: Verifica retorno de valuación numérica con HTTP 200.

4. **`ProductoRbacSecurityTest` (Control de Acceso):**
   - `POST /producto/crear` con rol `VENDEDOR` -> 403 Forbidden.
   - `PATCH /producto/actualizar/{id}` con rol `VENDEDOR` -> 403 Forbidden.
   - `DELETE /producto/borrar-producto-por-id/{id}` con rol `VENDEDOR` -> 403 Forbidden.
   - Peticiones anónimas a cualquier endpoint -> 401 Unauthorized estructurado.
